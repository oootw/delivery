# Аудит бэкенда (2026-07-11)

Диагностика по коду: мультитенантность, платежи/вебхуки, заказы, лояльность/промо,
транзакции, крон-процессы, безопасность, производительность. Сортировка по критичности.
Статус решения проставляется по мере фиксов.

## 🔴 Критично (целостность денег/баллов)

### 1. Оплата заказа и смена статуса — без транзакции — ✅ ИСПРАВЛЕНО
`RecordOrderPayment/Handler`, `ChangeOrderStatus/Handler`, `CancelOrder/Handler` делали
`orders->save()` и начисления/откаты баллов/скидок отдельными флашами. При падении между
ними — заказ в одном состоянии, леджер баллов/скидок в другом; повтор → двойное
начисление либо навсегда зависший резерв баллов. **Фикс:** записи обёрнуты в
`TransactionInterface::wrap` (как в PlaceOrder); realtime-уведомление и пересчёт ETA
вынесены за транзакцию (побочные эффекты, не должны ронять/откатывать платёж).

### 2. Заказ с итогом 0 ₽ невозможно оплатить → вечный `Created` — ✅ ИСПРАВЛЕНО
Калькулятор допускает `payable = 0`, если гость гасит всё баллами (`MIN_PAYABLE_KOPECKS`
в `PromotionPricing` защищает только промо+уровень, не списание баллов). CloudPayments не
проведёт 0 → нет вебхука `pay` → заказ навсегда `Created`, баллы зарезервированы, слот
промо занят. **Фикс:** `PlaceOrder` при `payableKopecks == 0` проводит оплату на сервере
в той же транзакции оформления (`registerPayment` → `finalizeOnPaid`), realtime+ETA — после
коммита; `PlacedOrderDTO.paymentRequired = false`, Action не отдаёт платёжный виджет
(ответ `payment_required: false`, без блока `payment`). Для 100% промо (без баллов) резерва
нет — finalize no-op. Ненулевой платёж ниже минимума CloudPayments (напр. 1 копейка) —
отдельный вопрос, здесь не трогаем.

### 3. Частичная идемпотентность начисления при завершении — ✅ ИСПРАВЛЕНО
`OrderRewards::accrueOnCompleted` страховался только `existsEarnForOrder()`. Без программы
кэшбэка (`earned==0`), но с картой штампов Earn-транзакция не писалась → повтор повторно
выполнял `recordSpend` (уровень) и `advanceStamps` (лишний штамп). **Фикс:** (а) Earn-запись
пишется ВСЕГДА (даже `points=0`) как единый маркер «за заказ начислено» — `existsEarnForOrder`
теперь коротит все эффекты, а не только кэшбэк; (б) партиальный уникальный индекс
`uniq_loyalty_earn_per_order (order_id) WHERE type='earn'` (миграция `Version20260711140000`)
отсекает гонку: параллельное завершение падает на констрейнте и откатывается целиком
(работает благодаря #1 — accrue внутри транзакции). **Данные:** при старых дублях Earn на один
заказ индекс не создастся — сначала дедуплицировать.

## 🟠 Логические ошибки

### 4. Слоты лимитированных промокодов утекают на неоплаченные заказы — ✅ ИСПРАВЛЕНО (крон истечения)
`PromotionPricing::recordApplied` вызывается в PlaceOrder (на создании, до оплаты):
инкрементит `redemptionsCount` и пишет `PromotionRedemption`. Откат — только при отмене.
Брошенный заказ навсегда съедал `maxRedemptions`/`maxRedemptionsPerCustomer`. **Фикс:**
выбран вариант «освобождать по истечении неоплаченных» (закрывает разом #4, #11 и часть #8).
Крон `app:orders:expire-abandoned` (use-case `Order/Command/ExpireAbandonedOrders`) отменяет
заказы в статусе `created` старше TTL (по умолчанию 30 мин, опция `--ttl`) и в одной
транзакции возвращает слот промо (`revertApplied`) и резерв баллов (`releaseOnCancel`) —
как в `CancelOrder`; realtime+ETA после коммита. Репозиторий: `findAbandonedCreated(createdBefore)`.
Фиксация промо оставлена на создании (не перенесена на оплату). **Остаётся:** гонка проверки
лимита и записи на последнем слоте (не атомарны) — общий долг конкурентности.

### 5. Вебхук отвечает `code:13` на уже обработанный платёж → бесконечные ретраи — ✅ ИСПРАВЛЕНО
`Order::registerPayment` бросал при статусе ≠ Created; вебхук возвращал `{code:13}`
(«повторяй») → дубликаты доставки ретраились вечно. **Фикс:** `Order::isAwaitingPayment()`
(status == Created); `RecordOrderPayment/Handler` при уже обработанном заказе идемпотентно
выходит (return) → Action отдаёт `code:0`, ретраи прекращаются.

### 6. Нет дедупликации вебхука по `TransactionId` — ✅ ИСПРАВЛЕНО (подписки)
Идемпотентность держалась только на статус-гардe; для подписок `registerPayment` каждый раз
продлевал период (повтор `pay` → двойное продление). **Фикс:** `Subscription` хранит
`lastPaymentTransactionId` (миграция `Version20260711150000`); `registerPayment` при том же
`transactionId` — no-op (возвращает false), Handler не сохраняет. `TransactionId` протянут
из webhook → `RecordSubscriptionPaymentCommand`. Заказы дедуплицируются статус-гардом (#5).

## 🟡 Пробелы для корректного SaaS

### 7. Подписка не enforce-ится нигде, кроме создания воркспейса — ✅ ИСПРАВЛЕНО
`past_due`/`canceled` не ограничивал работу: владелец редактировал, гости заказывали.
**Фикс:** `WorkspaceAccess::getOwnedWorkspace` теперь требует активную подписку владельца
(`requireActiveSubscription`) — гейт покрывает все ~28 владельческих мутаций разом (точки,
меню, промо, лояльность). Плюс новый `requireActiveWorkspace(workspaceId)`, который `PlaceOrder`
вызывает после расчёта: воркспейс без активной подписки заказы не принимает (гостевая витрина
«гаснет» на приёме заказа). Чтение (`requireMember`) и quote не трогаем. Grace/дюннинг не
вводили (без триала/грейса — по решению M1); возобновление — оплатой подписки.

### 8. Нет крон-процессов жизненного цикла — ✅ ИСПРАВЛЕНО
Было только `RecalculateWaitTimes`, `GrantAdmin`. **Сделано:**
- `app:orders:expire-abandoned` — истечение брошенных `Created`-заказов (см. #4), возвращает
  баллы и слоты промо.
- `app:subscriptions:cancel-past-due` (`--grace-days`, дефолт 3) — догоняющая отмена подписок,
  зависших в `past_due` дольше grace (страховка на пропущенный терминальный webhook; шлёт
  `cancelSubscription` в шлюз, сбой шлюза не мешает локальной отмене — устойчивая итерация).
  Use-case `Subscription/Command/CancelStalePastDueSubscriptions`, репо `findPastDueOlderThan`.
- `app:loyalty:expire-points` — FIFO-сгорание баллов старше `pointsLifetimeDays` каждой
  включённой программы. Чистый `Loyalty/Service/PointsExpiryCalculator` (лоты по начислениям,
  списания/прошлые сгорания «съедают» старейшие → идемпотентность между запусками); use-case
  `Loyalty/Command/ExpirePoints` пишет `Expire`-леджер, мутирует кошелёк под пессимистичной
  блокировкой (`getOrCreateForUpdate`, чтобы не затереть параллельный резерв), сжигает только
  из доступных (резерв не трогает). Новый тип леджера `LoyaltyTransactionTypeEnum::Expire`.

### 9. Рабочие часы точки не проверяются при заказе — ✅ ИСПРАВЛЕНО
`PlaceOrder` смотрел `isActive` и delivery/pickup, но не `WorkingHours` — заказы
принимались в нерабочее время. **Фикс:** чистые `WorkingHours::isOpenAt(weekday, HH:MM)`
и `Venue::isOpenAt(moment)` (переводит момент в таймзону точки, интервал полуоткрытый
[opens, closes), без перехода через полночь — гарантирует WorkingHoursRule). Калькулятор
получил флаг `requireVenueOpen` (бросает «Точка сейчас закрыта»); `PlaceOrder` передаёт
`true`, `QuoteOrder` — нет (предпросмотр цены доступен в любое время). Предзаказов на
будущее время нет — заказ принимается только когда точка открыта сейчас.

### 10. Enumeration аккаунтов + нет суточного лимита SMS — ✅ ИСПРАВЛЕНО (2026-07-12 — хвост закрыт)
`GetAuthCode` возвращал «Пользователь не найден» для незарегистрированного номера; дневного
лимита не было. **Фикс:** незарегистрированный номер получает такой же `success()` без
отправки SMS (эндпоинт больше не оракул существования аккаунта на один запрос); суточный
лимит запросов кода на номер (`GetSmsDailyLimitAvailable`, 10/сутки), проверяется ДО ветвления
по пользователю (единый ответ). Реализованы ранее застабленные `CodeRepository::countCreatedSince`
(реальный COUNT) и `create()` (проставляет `createdAt`/`expiresAt`, TTL 5 мин).
**Хвост закрыт (2026-07-12), все три вектора:**
- **Счётчик/кулдаун (decoy-записи).** `GetAuthCodeAction` реструктурирован: суточный лимит И
  кулдаун проверяются ДО ветвления по пользователю, а код выпускается **всегда** (для
  незарегистрированного — decoy-строка в `code` без SMS). Теперь лимит/кулдаун копятся
  одинаково независимо от регистрации; ветка «Код уже отправлен» больше не эксклюзив
  зарегистрированного.
- **Тайминг (async SMS).** Отправка SMS вынесена в Messenger async: порт
  `Authorize/Gateway/SmsSenderInterface` + адаптер `Infrastructure/Messenger/Sms/QueuedSmsSender`
  (dispatch `SendSmsMessage` → `SendSmsMessageHandler` зовёт `SMSManager`), routing в
  `messenger.yaml`, alias в `services.yaml`. `GetSmsCodeFetcher` больше не блокирует запрос на
  HTTP-вызове шлюза — тайминг веток выровнен. Побочно: сбой SMS не всплывает синхронно
  (ретраи очереди) — соответствует гайдлайну (уведомления async).
- **Единый ответ verify.** `AuthorizeAction`: убран `Assert::notNull($user, 'Пользователь не
  найден')`; код проверяется единообразно (для незарегистрированного есть decoy-код), при
  верном коде и `user===null` — тот же `'Неверный код'`, что и на неверный код. Оракул
  существования на эндпоинте проверки устранён.
- **Попутно (регрессия из #15).** `AuthorizeAction` ловил для 400 только `InvalidArgumentException`;
  после #15 `CheckOntimeCodeHandler` бросает `\DomainException` → неверный код улетал в `\Throwable`
  → 500. Ветка расширена до `catch (InvalidArgumentException | \DomainException)` → корректный 400.

Проверено: `lint:container` OK, `debug:messenger` (SendSmsMessage→handler) OK, `phpunit tests/Unit`
55/55, `php -l` OK. Миграций нет (decoy пишется в существующую таблицу `code`).
**Остаётся (осознанно):** decoy-строки чуть замусоривают `code` (чистятся сгоранием/ротацией по
TTL — не критично); dispatch async-сообщения для зарегистрированного добавляет sub-ms на enqueue
(в пределах сетевого шума, доминирующий блокирующий вызов шлюза устранён); глобального рейт-лимита
на IP нет — при желании позже.

**НАХОДКА (вне #10):** вся верификация кода была застаблена — вынесена в #15 (исправлено 2026-07-12).

### 11. Race окна `quote→reserve` баллов — ✅ ИСПРАВЛЕНО
Два параллельных заказа могли зарезервировать больше доступного баланса (`reserve` без
блокировки). **Фикс:** `LoyaltyAccountRepository::getOrCreateForUpdate` читает строку кошелька
с пессимистичной блокировкой (`SELECT … FOR UPDATE`); `reserveOnPlace` (внутри транзакции
`PlaceOrder`) использует его → конкурентный резерв дожидается коммита и перечитывает свежий
`reservedPoints`, `LoyaltyAccount::reserve()` бросает на нехватке. Домен-guard уже был; не
хватало сериализации на уровне БД.

## 🔵 Производительность / прочее

### 12. Сканирование ФС в цикле по товарам — ✅ ИСПРАВЛЕНО
`MenuImageStorage::findItemGallery` делал до 24 `is_file()` на товар; в `GetMenu`/
`GetClientProducts` умножалось на число позиций (≈1200 stat на категорию из 50 товаров).
**Фикс:** приватный кеш листинга каталога `{slug}` на время запроса (`directoryIndex`,
один `scandir` на slug); чтение (`findUrl`/`findItemGallery`) проверяет наличие в памяти
(`fileExists`), а не через syscall. Запись/удаление (`store`/`delete`/`addToItemGallery`/
`deleteItemGalleryIndex`) инвалидируют кеш slug. Сервис живёт в рамках запроса (FPM), так
что кеш не устаревает между запросами.

### 13. Дубли пендинг-подписок/промокодов — ✅ ИСПРАВЛЕНО
Промокод: БД-констрейнт **уже был** — partial-unique `uniq_promotion_workspace_code
(workspace_id, code) WHERE code IS NOT NULL` (миграция `Version20260709120000`), гонка падает
на индексе. **Фикс дублей pending:** `StartSubscription` теперь переиспользует существующую
pending-подписку пользователя (`findPendingByUser`), меняя тариф через `changePendingTarif`
(guard: только статус pending), вместо создания новой строки. Одна pending на пользователя.

### 14. Откаты вне транзакции — ✅ ИСПРАВЛЕНО вместе с #1
`revertApplied`/`releaseOnCancel` при отмене шли отдельными флашами (частичное состояние).
Обёрнуто в транзакцию вместе с п.1.

## 🔴 Новые находки

### 15. Верификация кода авторизации застаблена (найдено при #10) — ✅ ИСПРАВЛЕНО (2026-07-12)
`CodeRepository::validateCode()` и `validateCodeByCreatedAt()` возвращали `true` **всегда** —
любой введённый код проходил проверку, кулдаун между отправками не действовал. **Согласовано:**
одноразовость (код сгорает после успешного входа), TTL 5 мин (был), **3 попытки** до сгорания,
код **4 цифры** (оставлен), кулдаун повторной отправки **60 сек**. **Фикс:** застабленные
методы репозитория заменены на реальный доступ к данным — `findActiveCode(phone, codeType)`
(последний выпущенный код), `hasRecentCode(phone, since)` (кулдаун), `save(Code)` (персист
`attempts`/`usedAt`); бизнес-логика вынесена из репозитория в домен (методы `Code::matches`
через `hash_equals`, `isExpiredAt`, `isUsed`, `registerFailedAttempt`, `hasReachedAttemptLimit`,
`markUsed`) и `CheckOntimeCodeHandler` (порядок гардов: нет кода → использован → истёк →
лимит попыток → сравнение; неверный код инкрементит попытку и на лимите сжигает код, `\DomainException`
на русском). `GetSmsCodeSendAvailableFetcher` считает кулдаун через `hasRecentCode(-60 sec)`.
Схема: колонки `used_at` (nullable) + `attempts` (int default 0) в таблице `code`, миграция
`Version20260712120000`. Unit-тесты: `tests/Unit/Authorize/CodeTest`, `CheckOntimeCodeHandlerTest`
(12 тестов). Проверено: `lint:container` OK, `doctrine:mapping:info`/`schema:validate` OK,
`phpunit tests/Unit` — 55/55. **Пользователю: прогнать миграцию `Version20260712120000`.**
**Остаётся (осознанно):** брутфорс-защита держится на счётчике попыток на код + суточном лимите
SMS (#10); отдельного глобального рейт-лимита на эндпоинт проверки нет — при желании добавить
позже. Квирк запроса `codeType='register'` при внутреннем хранении `authorize` не трогал (вне #15).
