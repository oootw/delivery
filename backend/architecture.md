## Правила реализации бэкенда (Delivery, Symfony 8.1, Doctrine, DDD)

Этот документ описывает единые правила разработки бэкенда проекта на PHP 8.4 с использованием Symfony 8.1, Doctrine ORM 3 и DDD-подхода (порты и адаптеры). Все новые реализации должны строго соответствовать этим правилам.

> Исторически проект начинался с гайдлайна под Bitrix + Slim. Здесь те же принципы переложены на Symfony: место Bitrix-инфоблоков занимает Doctrine ORM, место Slim Actions — Symfony-контроллеры (`AbstractController` + атрибуты `#[Route]`), место Bitrix-событий — `EventDispatcher` и Messenger.

---

## 1. Общая архитектура и слои

- **Версия PHP**: 8.4, в каждом файле ставим `declare(strict_types=1);`.
- **Пространство имён**: все классы в `App\...` (PSR-4: `App\` → `src/`).
- **Фреймворк**: Symfony 8.1 (framework-bundle, security-bundle, doctrine-bundle, messenger, monolog, mercure).
- **HTTP**: контроллеры-действия под `/api/v1`, маршруты объявляются атрибутами `#[Route]` и автозагружаются из `config/routes.yaml`.
- **DI-контейнер**: штатный Symfony-контейнер, автоконфигурация и автовайринг через `config/services.yaml`. Дополнительные аргументы (ключи, TTL) прокидываются параметрами из окружения (см. блок `services:` в `services.yaml`).
- **База данных**: PostgreSQL 16 через Doctrine DBAL/ORM. Схема управляется миграциями (`doctrine-migrations-bundle`, каталог `migrations/`).

- **Три слоя приложения**:
  - **`src/Application/{Domain}`** — доменный слой: сущности домена, интерфейсы репозиториев (порты), команды/обработчики, запросы/фетчеры, доменные сервисы и события. Этот слой не знает про Doctrine, HTTP и внешние API.
  - **`src/Infrastructure`** — адаптеры: Doctrine-сущности (ORM-мэппинг) и реализации репозиториев, клиенты внешних систем (CloudPayments, iiko, rkeeper), интеграции.
  - **`src/Http`** — транспортный слой: контроллеры-действия и безопасность (JWT).
  - **`src/Shared`** — переиспользуемое между доменами: сервисы (`SMSManager`, `JWTManager`, `LoggerService`), enum'ы, value-object'ы, трейты.

- **DDD-границы**:
  - Внешний мир (HTTP, Messenger, webhooks) общается с доменом только через **Command → Handler**, **Query → Fetcher** и **обработчики событий**.
  - Доменные сущности и сервисы **не вызываются напрямую** из контроллеров — только через Handler/Fetcher.
  - Домен обращается к БД и внешним системам **только через интерфейсы репозиториев/клиентов** (порты), объявленные в `Application`. Реализации живут в `Infrastructure`.
  - Агрегаты и value-object'ы используем только по реальной необходимости, без усложнения.

## 2. Структура доменов

- **Корень домена**: `src/Application/{Domain}` (например, `src/Application/Workspace`).

- **Подпапки домена**:
  - `Entity/{Entity}/` — доменная сущность и порт репозитория:
    - `{Entity}.php` — доменная сущность (чистый PHP, без Doctrine-атрибутов).
    - `{Entity}RepositoryInterface.php` — интерфейс репозитория (порт).
    - `{Entity}CodeEnum.php`, `{Entity}StatusEnum.php` и т.п. — enum'ы, относящиеся к сущности.
  - `Command/{UseCase}/` — команда на изменение состояния:
    - `Command.php` — DTO команды.
    - `Handler.php` — обработчик use-case.
    - `{Result}DTO.php` — DTO результата (при необходимости).
  - `Query/{UseCase}/` — запрос на чтение:
    - `Query.php` — DTO запроса (при необходимости).
    - `Fetcher.php` — фетчер, возвращающий DTO/массивы.
    - `{Result}DTO.php` — DTO результата.
  - `Service/{ServiceName}/` — доменные сервисы (например, `WaitTimeEstimator`).
  - `Events/{EventName}/` — доменные события (POPO-объект события + payload при необходимости).

- **Инфраструктура домена**: `src/Infrastructure/Doctrine/Domain/{Domain}/`:
  - `{Entity}.php` — Doctrine ORM-сущность с атрибутами `#[ORM\...]`.
  - `{Entity}Repository.php` — реализация `..RepositoryInterface`, наследует `ServiceEntityRepository`.

- **HTTP-слой**: `src/Http/Action/{Domain}/{UseCase}Action.php`.

---

## 3. HTTP-слой (Symfony Actions)

- **Расположение**: `src/Http/Action/{Domain}/{UseCase}Action.php`.
- **Базовый класс**: наследуем `Symfony\Bundle\FrameworkBundle\Controller\AbstractController`.
- **Один Action — один use-case**. Метод обработки называем `handle`.
- **Маршрут**: атрибут `#[Route('/path', name: 'app_...', methods: ['POST'])]`.
  - Публичные маршруты авторизации автозагружаются с префиксом `/api/v1/auth`, остальные — с `/api/v1` (см. `config/routes.yaml`).
- **Конструктор**:
  - Внедряем Handler'ы и Fetcher'ы через DI.
  - Свойства — `private readonly`.
  - При создании Command/Query используем **именованные аргументы**.

- **Метод `handle(Request $request): Response`**:
  - Читаем тело/параметры: `$request->toArray()`, `$request->query->all()`, `$request->files`, атрибуты маршрута.
  - Валидируем вход утверждениями `Webmozart\Assert\Assert` — при нарушении летит `InvalidArgumentException`.
  - Создаём Command/Query и вызываем `handler->handle(...)` / `fetcher->fetch(...)`.
  - Нормализуем результат к массиву и возвращаем `$this->json([...])`.
  - **Единственный внешний `try-catch`**:
    - `InvalidArgumentException` (нарушение `Assert`) и `\DomainException` (бизнес-ошибка из домена) → `Response::HTTP_BAD_REQUEST` (400) с человекочитаемым `error`; при необходимости добавляем машинный `code` (например, `USER_EXIST`). Обычно ловим их одним `catch (InvalidArgumentException | \DomainException $e)`.
    - Остальные `\Throwable` → логируем `LoggerService::toFile('домен/use-case', $e->getMessage())` и отдаём 500 с нейтральным сообщением.
  - Формат ответа единый: `['is_success' => bool, ...]`, ошибки — `['is_success' => false, 'error' => '...']`.

- **Где допустим `try-catch`**: по умолчанию — **только в Action**. В нижних слоях (репозитории, сущности, доменные и простые сервисы) `try-catch` используем лишь в крайнем случае (например, обёртка вокруг вызова внешнего SDK, где нужно перевести чужое исключение в доменное, или итеративная обработка, где сбой одного элемента не должен ронять весь процесс). Во всех остальных случаях внутри домена не ловим исключения, а бросаем `\DomainException` и даём ему всплыть до Action.

## 4. Команды (Command) и обработчики (Handler)

- **Расположение**: `src/Application/{Domain}/Command/{UseCase}/`.

- **Command**:
  - Лёгкий DTO без логики.
  - Свойства `public readonly`, строго типизированы, задаются через конструктор именованными аргументами.

- **Handler**:
  - Namespace `App\{Domain}\Command\{UseCase}`.
  - Конструктор внедряет **интерфейсы** репозиториев и доменные сервисы; свойства — `private readonly`.
  - Имена свойств-репозиториев — во **множественном числе по имени сущности, без суффикса** `Repository` (например, `$users` для `UserRepositoryInterface`, `$workspaces` для `WorkspaceRepositoryInterface`).
  - Метод `handle(Command $command)`:
    - Возвращаемый тип строгий: DTO при обязательном результате, `void` при команде без результата, `?DTO` — если результат может отсутствовать.
    - Внутри — только доменная логика: работа с сущностями, вызовы репозиториев и других доменных сервисов.
    - Бизнес-ошибки — `throw new \DomainException('Сообщение на русском')`.
    - Никакого Doctrine/HTTP/внешних SDK напрямую — только через порты.

---

## 5. Запросы (Query) и фетчеры (Fetcher)

- **Расположение**: `src/Application/{Domain}/Query/{UseCase}/`.

- **Query**: DTO без логики (создаём, если есть входные параметры).

- **Fetcher**:
  - Namespace `App\{Domain}\Query\{UseCase}`.
  - Метод `fetch(Query $query): DTO|array`.
  - Возвращает DTO, массив DTO или ассоциативный массив.
  - Знает только про домен и порты репозиториев; не знает про HTTP и Doctrine.
  - Фетчеры и Handler'ы **не описываем вручную** в DI — они регистрируются автоконфигурацией через `App\: '../src/'`.

---

## 6. Доменные сущности (Application/Entity)

- **Расположение**: `src/Application/{Domain}/Entity/{Entity}/{Entity}.php`.
- **Назначение**: чистая доменная модель, независимая от Doctrine. С ней работают Handler'ы/Fetcher'ы, её возвращают репозитории.

- **Требования**:
  - Namespace `App\{Domain}\Entity\{Entity}`.
  - Свойства — `public` (и, как правило, `readonly`), строго типизированы. Идентификатор — `id`, для новой ещё не сохранённой сущности допустим `?int $id = null`.
  - Статический конструктор `buildNew(...)`:
    - Создаёт новую сущность из доменных параметров именованными аргументами.
    - `id` для новой сущности — `null`.
    - **Не** валидирует обязательные поля и **не** бросает исключений — только сборка объекта.
  - Бизнес-правила проверяем в доменных методах сущности (если они есть) либо в Handler/Service, **не** в `buildNew`.
  - Геттеры/сеттеры не плодим — только при реальной необходимости (например, проставить сгенерированный `id` после сохранения).

---

## 7. Doctrine-сущности и репозитории (Infrastructure)

- **Расположение**: `src/Infrastructure/Doctrine/Domain/{Domain}/`.
- Doctrine-мэппинг сканируется только из `src/Infrastructure/Doctrine/Domain` (см. `config/packages/doctrine.yaml`).

- **Doctrine-сущность (`{Entity}.php`)**:
  - Атрибуты `#[ORM\Entity(repositoryClass: {Entity}Repository::class)]`, `#[ORM\Table(...)]`, `#[ORM\Column(...)]`.
  - Private-свойства с геттерами/сеттерами (стандартный стиль maker-bundle).
  - Это **инфраструктурная** модель хранения; в домен её не отдаём — репозиторий мэппит её в доменную сущность из `Application`.

- **Репозиторий (`{Entity}Repository.php`)**:
  - Наследует `Doctrine\Bundle\DoctrineBundle\Repository\ServiceEntityRepository` и реализует `App\{Domain}\Entity\{Entity}\{Entity}RepositoryInterface`.
  - Отвечает за:
    - Чтение/запись через Doctrine (QueryBuilder / EntityManager).
    - Маппинг Doctrine-сущности в доменную сущность (`{DomainEntity}::buildNew(...)`).
    - Диспатч доменных событий через `EventDispatcherInterface`, если это часть контракта сохранения.
    - Генерацию доменных исключений при ошибках.
  - **`try-catch` в репозиториях запрещён** — исключение кидаем напрямую.

- **Сигнатуры методов**:
  - Метод, который **обязан** вернуть результат: имя начинается с `get...`; при отсутствии данных — `throw new \DomainException('...на русском...')`.
  - Метод, который **может** не вернуть: имя начинается с `find...`; возвращаем `null` (`?Entity`, `?array`).
  - Коллекции: `findAllBy...` / `getAll...`; при отсутствии — пустой массив, либо `\DomainException`, если пустой результат по бизнес-логике ошибка.

- **Исключения**:
  - `\DomainException` и `\Throwable` **не импортируем** через `use` — пишем полное имя со слэшем.
  - Сообщения — на русском, конкретные.

- **Мультитенантность**: тенант-таблицы содержат `workspace_id`; репозитории обязаны фильтровать выборки по текущему воркспейсу. Идентификатор текущего воркспейса берём из контекста запроса (см. раздел 12), а не из глобальных переменных.

---

## 8. События и Messenger

- **Доменные события**:
  - Расположение: `src/Application/{Domain}/Events/{EventName}/`.
  - Событие — простой объект (POPO) с публичными свойствами; диспатчится через `Symfony\Component\EventDispatcher\EventDispatcherInterface` (обычно из репозитория, до/после сохранения).
  - Слушатели/подписчики регистрируются автоконфигурацией (`#[AsEventListener]` / `EventSubscriberInterface`).

- **Асинхронная обработка (Messenger)**:
  - Тяжёлые и внешние операции (импорт меню из iiko/rkeeper, отправка уведомлений, синхронизация статусов заказов) оформляем как Messenger-сообщения и роутим в транспорт `async` (см. `config/packages/messenger.yaml`).
  - Message — DTO без логики; MessageHandler помечаем `#[AsMessageHandler]` и держим тонким: он извлекает данные и вызывает доменный Handler/Fetcher.
  - Внутрь домена передаём **только нужные данные**, а не целиком объект сообщения/события.

---

## 9. Внешние интеграции (платежи, POS-системы)

- **Порт в домене**: интерфейс клиента объявляем в `Application` (например, `PaymentGatewayInterface`, `PosMenuProviderInterface`).
- **Адаптер в инфраструктуре**: реализация под конкретного провайдера в `src/Infrastructure/{Provider}/` (CloudPayments; iiko/rkeeper под общим портом POS).
- Сгенерированные из OpenAPI SDK живут в `libs/` (PSR-4 в `composer.json`) и используются **только** из адаптеров инфраструктуры, никогда из домена.
- Webhooks (например, CloudPayments) принимаем отдельным Action, проверяем подпись в адаптере, дальше — через Command/Handler.

---

## 10. Безопасность (JWT)

- Аутентификация — stateless JWT (`lcobucci/jwt`) через `App\Http\Security\JwtAuthenticator`.
- Firewall'ы (`config/packages/security.yaml`): `/api/v1/auth` — публичный, `/api/v1` — требует валидный токен.
- Токены выпускаются доменом `Authorize` (`JWTManager` из `Shared`), refresh/logout — отдельными use-case'ами.

---

## 11. Стиль кода и соглашения

- **Типизация**: `declare(strict_types=1);`, явные типы аргументов и возвращаемых значений; `mixed` не используем для обязательных результатов.
- **Именованные аргументы**: при создании сущностей, Command/Query, DTO — обязательно (`Workspace::buildNew(name: $name, slug: $slug, ownerId: $ownerId)`).
- **Имена**:
  - Читаемость важнее краткости; код должен читаться линейно, сверху вниз (высокий уровень абстракции — вверху, детали — ниже).
  - Классы — существительные, методы — глаголы.
  - **Запрещены «пустые» и жаргонные имена**: `ensure`, `resolve`, `handle*Data`, `process`, `manager`-обёртки без смысла, сокращения вроде `neast`. Имя должно объяснять намерение (`estimateWaitTime`, `findBySlug`, `markOrderReady`).
  - Не плодим неотличимые пары (`Data`/`Info`).
- **Исключения**: бизнес-ошибки — `\DomainException` с русским сообщением; `\DomainException`/`\Throwable` без `use`.
- **Логирование**: только `App\Shared\Service\LoggerService\LoggerService::toFile('домен/use-case', $message)`; имя лога в формате `домен/use-case` через дефис.
- **Чистота**: неиспользуемые `use` удаляем; PSR-12; доступ к зависимостям только через DI; глобальных переменных нет.
- **Комментарии**: объясняем намерение кодом, а не комментарием. Комментарий уместен только там, где логику нельзя выразить именем (нетривиальная формула, ссылка на внешнее требование).

---

## 12. Контекст воркспейса

- Текущий воркспейс определяется по поддомену `slug.app.com` (или заголовку/маршруту — уточняется отдельно).
- Резолвинг воркспейса выполняется в HTTP-слое (например, в подписчике запроса), кладётся в контекст запроса и передаётся в Command/Query **явным параметром** (`workspaceId`), а не через глобальное состояние.
- Все тенант-репозитории обязаны фильтровать данные по `workspaceId`.

---

## 13. Поток обработки HTTP-запроса

1. Запрос `POST /api/v1/...` попадает в Symfony, проходит firewall (JWT для приватных маршрутов).
2. Роутинг по атрибуту `#[Route]` находит Action.
3. Action: читает тело/параметры → валидирует `Assert` → собирает Command/Query (именованные аргументы) → вызывает Handler/Fetcher → нормализует результат → `$this->json(...)`.
4. Handler/Fetcher: доменная логика через порты репозиториев и доменные сервисы.
5. Репозиторий (Infrastructure): Doctrine-запрос, маппинг в доменную сущность, при необходимости — диспатч события; тяжёлое/внешнее уходит в Messenger `async`.

**Границы DDD**: HTTP ↔ Домен — только через Command/Query; Домен ↔ БД/внешние системы — только через интерфейсы репозиториев/клиентов.

---

## 14. Обязательное и запрещённое

- **Обязательно**:
  - Повторять структуру существующих доменов (`Authorize`, `Tarif`, `Workspace`): `Entity` + `RepositoryInterface` (Application), Doctrine-сущность + репозиторий (Infrastructure), `Command/Handler`, `Query/Fetcher`, `Http/Action`.
  - Держать домен свободным от Doctrine/HTTP/внешних SDK.
  - Фильтровать тенант-данные по `workspaceId`.
- **Запрещено**:
  - Doctrine/HTTP/внешние SDK в доменном слое (`Application`).
  - `try-catch` в репозиториях, сущностях и простых сервисах — кроме крайних случаев (перевод чужого исключения из внешнего SDK в `\DomainException`, устойчивая итеративная обработка). По умолчанию ловим только в Action, внутри домена — бросаем `\DomainException`.
  - Валидация и бросание исключений в `buildNew`.
  - Передача внутрь домена целых объектов запроса/события/сообщения — только извлечённые данные.
  - Геттеры/сеттеры в доменных сущностях без необходимости.
  - «Пустые» имена (`ensure`, `resolve`, `process`, безликие `Manager`/`Data`).

---

Соблюдение этих правил обязательно для всех новых реализаций. При доработке существующих доменов приводим код к этим соглашениям, не ломая текущую бизнес-логику.
